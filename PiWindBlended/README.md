# PiWind Blended

Toy UK windstorm and storm surge model for exposures known only at postcode level, using
**blended areaperils**.

> **Requires** an oasislmf with blended areaperil support (gulmc, and getmodel/gulpy for the
> per-item marginal). An older oasislmf does not recognise `blended_areaperil_id.csv`, reads the
> blended ids as cells with no hazard, and `tests/test_1` completes with zero losses, so its expected
> results do not match.

## The idea

A postcode covers several hazard cells. PiWind Postcode handles this by merging the cells' hazard
into a single postcode footprint before sampling. That gets each peril's distribution right for one
location, but the building's position is no longer a variable, so nothing keeps wind and surge (or
buildings and contents) consistent about where the building stands.

A blended areaperil keeps the position. Each postcode is a set of **candidate positions** with
weights. In every sample the engine places each building at one position, and every peril and
coverage of that building reads the hazard of the cell covering that position. The placement is the
same for every event within a sample, and buildings of a multi-building location are placed
independently.

## How the model data is built

Everything is generated by `src/build_blended_model.py` from PiWind and PiWind Postcode data; rerun
it to rebuild `keys_data/`, `model_data/` and the test exposures.

- **Wind** keeps PiWind's 10x10 grid, areaperils 1-100.
- **Surge** is re-gridded onto a coarser 7x7 grid over the same extent, areaperils 101-149. A
  coarse cell takes the highest surge intensity of the PiWind cells it overlaps. Because 7 does not
  divide 10 the two grids do not nest, so a postcode's positions are a genuine overlay: two
  positions can share a wind cell and differ in surge cell, and the reverse.
- **Positions and weights** come from the built environment used by PiWind Postcode
  (`../PiWindPostcode/src/exposure_modification/OEDLocBuiltEnv.csv`, 12,598 buildings in 524
  postcodes). Each building falls in one wind cell and one surge cell; a position is a distinct
  (wind cell, surge cell) pair holding at least one building of the postcode, and its weight is the
  building count. Postcodes have up to 7 positions, 1.85 on average.

### Identifier bands

| ids | meaning |
|---|---|
| 1-100 | wind cells (PiWind grid) |
| 101-149 | coarse surge cells |
| 1001-1524, 2001-2524 | collapsed postcode areaperils, wind and surge |
| 10001-10524, 20001-20524 | blended areaperils, wind and surge |

The blended and placement-scheme ids are numbered from the postcode index (scheme `k`, blended ids
`10000+k` and `20000+k`). That is for readability only: the engine treats all of these ids as opaque.

### `model_data/blended_areaperil_id.csv`

```
blended_areaperil_id,placement_scheme_id,placement_id,weight,areaperil_id
10001,1,0,5,26
10001,1,1,5,27
10001,1,2,22,36
10001,1,3,1,37
...
20001,1,0,5,108
...
```

One row per (blended id, position). Both blended ids of a postcode name the same
`placement_scheme_id`, list the same `placement_id`s with the same `weight`s, and differ only in
`areaperil_id`, the cell covering that position for their peril. Weights are integer building
counts.

### The collapsed control

`lookup_config_collapsed.json` returns postcode areaperils whose footprint is the count-weighted
mixture of each peril's cells, built from exactly the same positions and weights. It is the
PiWind Postcode method, with one difference: where a cell has no hazard for an event, its weight goes
to a dedicated intensity bin 59, which every vulnerability maps to zero damage, instead of being
renormalised away. This keeps the collapsed control mean-correct, so comparing the two runs shows
what blending changes (dispersion and cross-peril consistency) without a bias in the mean as well.
The vulnerability file is PiWind's plus that bin.

## Tests

Both tests use the same exposure: ten postcodes whose positions straddle the surge strip (13% to 86%
of their buildings on cells that see surge), one single-building location each, plus two 12-building
locations in the first two postcodes.

| test | lookup | what it shows |
|---|---|---|
| `test_1` | `lookup_config_blended.json` | per-sample placement: each building stands at one position per sample, shared by its perils and coverages |
| `test_2` | `lookup_config_collapsed.json` | the merged-footprint approach on the same data |

Run either with `oasislmf model run -C oasislmf.json` from the test directory. Both use gulmc.

## Not covered by this model

- **Unknown occupancy (1000).** PiWind Postcode maps it to aggregate vulnerabilities weighted by
  `areaperil_id`; how those weights should key on a blended id is not defined yet, so here occupancy
  1000 uses PiWind's default vulnerabilities.
- **Weights that differ by building type.** The interface allows a different scheme for, say,
  commercial and residential locations in the same postcode; this model uses one scheme per postcode.
- **Return-period protection** of individual positions.
